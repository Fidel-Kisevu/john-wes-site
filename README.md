# John Wes — Public Site & Publishing Desk

A modern, modular React application built with Vite, TypeScript, Tailwind CSS, React 19, and TanStack Start/Router. The project follows a strict Smart/Dumb Component architecture so that data loading, route logic, and UI rendering are cleanly separated.

This makes the codebase easier to extend, safer to edit, and much easier for future contributors to understand.

---

## 🏗️ Architecture: The Smart/Dumb Pattern

Every page in this project is built using two layers:

1. The Smart Route (`src/routes/...`)
   - Handles routing, validation, loaders, and data access.
   - Passes fetched data into a presentational component.
   - Contains almost no raw HTML or Tailwind class markup.

2. The Dumb View (`src/components/shared/...`)
   - Renders the UI.
   - Receives typed props and outputs the final layout and Tailwind classes.
   - Contains no data-fetching or route logic.

This separation keeps the app scalable and avoids mixing business logic with presentation.

Because the app is split into smart routes and presentational views, the visual work usually lives in `src/components/shared/` rather than in the route files.

## 🧠 How the Data Flows

1. The route file in `src/routes/` loads data using the CMS layer.
2. The CMS reads from project data sources and shared content types.
3. The route receives the data and passes it down to a view component.
4. The view component renders the final markup and classes.

Example pattern:

```tsx
import { createFileRoute } from '@tanstack/react-router'
import { loadHomepage } from '@/lib/cms'
import { HomeView } from '@/components/shared/home/HomeView'

export const Route = createFileRoute('/')({
  loader: () => loadHomepage(),
  component: HomeRoute,
})

function HomeRoute() {
  const data = Route.useLoaderData()
  return <HomeView data={data} />
}
```

This pattern is used across the app: the route handles the data contract, while the view handles the rendering.

## 🚀 Getting Started

### Prerequisites

- Node.js 22
- npm

### Installation

```bash
npm install
```

### Development

Run the app locally:

```bash
npm run dev
```

If you are on Windows PowerShell:

```powershell
cd minister-benja
npm install
$env:VITE_AUTH_ENABLED = "false"
npm run dev
```

If you are on macOS or Linux:

```bash
cd minister-benja
npm install
VITE_AUTH_ENABLED=false npm run dev
```

Then open the app at:

- Public site: http://localhost:8080
- Admin desk: http://localhost:8080/admin

With `VITE_AUTH_ENABLED` set to `false`, the desk opens in local editor mode. Leave that unset when using the hosted preview flow that authenticates through the app environment.

### Type Checking

```bash
npm run typecheck
```

### Production Build

```bash
npm run build
```

## ⚠️ Important Rules for Contributors

1. Do not hand-edit `src/routeTree.gen.ts`.
   It is generated automatically by TanStack Router.

2. Keep routes thin.
   If a route file starts getting large or contains lots of JSX, move that markup into `src/components/shared/`.

3. Keep the Smart/Dumb split intact.
   Route files should load data and pass props; view components should render markup.

4. Use the `@/` alias for imports.
   Prefer `@/components/...`, `@/lib/...`, and `@/routes/...` over deep relative imports.

5. Preserve the visual structure when editing classes.
   The layout is intentionally precise; changes to Tailwind markup should be tested in-browser.

6. Do not mix CMS logic into the UI layer.
   Data fetching belongs in the route or `src/lib`, not in the presentational components.

---

## 🧭 Practical Contributor Workflow

When making a change, use this rule of thumb:

- If you are changing data or route behavior: edit the route or the loader in `src/lib`.
- If you are changing page structure, spacing, typography, or layout: edit the view in `src/components/shared/`.
- If you are changing the global shell or site-wide chrome: edit the components under `src/components/layout/` or `src/styles.css`.

That pattern keeps the codebase consistent and avoids accidental UI drift.

## ✅ Project Summary

John Wes is a modular publishing and ministry site with a strong separation between content logic and rendering. The architecture is intentionally designed to scale with future pages, features, and content types while keeping layout work predictable and safe.

The app is built to be easy to maintain across multiple workstreams:

- public content pages
- essay and book presentation
- message archives and teaching content
- admin desk workflows
- shared page layout and design tokens

This project is a good example of a clean, component-driven content site architecture in React and TanStack.
